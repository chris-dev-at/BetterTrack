## 1. Vision & Goals

BetterTrack is a self-hosted **personal finance and investing workspace**: users track multiple portfolios, browse assets, build **Conglomerates** (ETF-style weighted baskets), backtest strategies, turn budgets into buy lists, share portfolios and ideas with friends, and — later — connect their own tools through an API.

The app is organized around **five workspaces on one navigation rail** (the V1 five-area list "Portfolio | Workboard | Assets | Social | Profile Menu" was superseded by the V6-1 Origin shell — §16 2026-09-02):

**Home | Portfolio | Workbench | Assets | People** — plus the **Control Center** (settings) and the account menu (§6.11, §7.2)

**Core promises:**

1. **Track** — record real buys/sells; see value, profit/loss, top winners/losers and history of everything you own, market-listed or not (your car, your house, an unlisted stock). Multiple portfolios (private, firm, shared) are the design target; V1 ships one default portfolio on a multi-portfolio data model.
2. **Play** — the Workboard is a financial playground: watchlists, Conglomerates with percentage weights, backtests, and a budget calculator that turns "1000 €" into a concrete buy list (whole-share or fractional) that never overshoots.
3. **Browse** — the Assets section is a full asset browser with a **local search index**: searching "bayer" hits BetterTrack's own catalog, not a live provider round-trip. Asset pages chart history and offer quick actions into the rest of the app.
4. **Share** — add friends inside BetterTrack; share a portfolio read-only with friends (V1); later: shared/editable portfolios, ideas, public profiles and links.
5. **Private & polite** — closed by default (admin decides the registration mode); the server does almost nothing while nobody interacts; upstream data providers are never spammed — everything is cached and coalesced.

**Non-goals (V1):** not a broker (no order execution), no investment advice, no mobile app / Firebase, no bank APIs, no public social network (feed/comments/likes/chat), no OAuth app marketplace, no second-by-second Live Mode streaming, no Google Drive backups.

**Success criteria for V1:** an invited user logs in, finds BAYN.DE instantly via local search, watches it, builds a 13/40/47 Conglomerate, backtests it, turns 1000 € into a buy list, records those buys next to their house in their portfolio, flips "share with friends" on, and their friend sees the portfolio read-only under Shared With Me — with a bell notification and a logged email on the way. The admin manages accounts and global app settings from a separate admin area and has **no** portfolio of their own. All five tabs exist; not-yet-built surfaces say "Coming soon" instead of not existing.

## 2. Glossary

| Term | Meaning |
|---|---|
| **Asset** | Anything trackable with a price/value over time. Market assets come from a data provider; **custom assets** (house, car, unlisted stock) get their values from the user. One unified concept — charts, portfolio math and backtests treat them identically. |
| **Asset catalog** | BetterTrack's own Postgres-backed index of known assets, powering **local search** (§6.2). Providers fill it; users search it. |
| **Provider** | A pluggable source of asset data implementing the `AssetProvider` interface. V1: `yahoo` (market data) and `manual` (custom assets). |
| **Quote** | Latest known price of an asset + day change, currency, timestamp. |
| **Portfolio** | A record of real ownership, derived from transactions. A user can have several (V1: one default; schema is multi-portfolio). Has a **visibility**: `private` or `friends` (read-only). |
| **Transaction** | One buy or sell: asset, quantity, price, fee, timestamp. |
| **Custom investment** | A user-created asset with manually entered **value points**; values carry forward between points. |
| **Workboard** | The playground tab: watchlist, Conglomerates, backtests, calculators; later comparisons and saved ideas. Watching ≠ owning. |
| **Conglomerate** | A named basket of assets with percent weights summing to 100 — the user's "own ETF". |
| **Position** | One entry of a Conglomerate: asset + weight percent. |
| **Backtest** | Historical performance of a Conglomerate, computed from daily closes as a weighted buy-and-hold index. |
| **Invest Calculator** | Turns (Conglomerate + budget) into a concrete buy list, whole-share or fractional, never exceeding budget. |
| **Friend** | A mutual, accepted connection between two users. Created via friend request (by username or email); either side can remove it. |
| **Live Mode** | An asset-chart mode showing short real-time windows (1 m … 12 h) fed by **one shared stream per asset** regardless of viewer count. V1: button exists, marked Coming soon. |
| **Alert** | A rule on an asset (price above/below, ±X%) that fires a notification. Designed (schema exists), **post-v1**. |
| **Notification channel** | Pluggable delivery: in-app + email (V1); phone push / Telegram / Discord later. |
| **Email log** | Per-user record of every email the system sent (or failed to send) for that user; visible to the admin. |
| **Registration mode** | Global admin setting for how accounts come to exist: closed · invite/token · approval · open (§6.12). |
| **Account kind** | `user` (uses the app) or `admin` (management-only; no portfolio, no user features — §3). |
| **Coming Soon page** | A real routed page/section rendered as a designed placeholder, so the final structure is visible before the feature ships. |
| **Base currency** | Currency everything is converted to for totals/charts. V1: EUR (per-user setting is a Future Feature). |

## 3. Users & Access Model

- **User** — a normal account. Has email (required), username, password. Uses the entire app. Sees other users' data only through Social: portfolios friends explicitly shared, plus (later) shared links/profiles.
- **Admin** — a **management-only account kind**, not a superpowered user. Admins administer the system in their own admin area (served on the admin origin, §4.6/§11): accounts, invites, audit log, email log, global app settings. Admins have **no portfolio, no workboard, no friends — no user-app features at all**; the user API rejects admin sessions and vice versa. If an admin wants to try the app, they create a separate test user account. Admin cannot browse users' portfolios (privacy stance — deliberate).
- **Friends** — users connect via friend requests (username or email). Friendship is mutual and revocable; it is the only V1 sharing audience.
- **How accounts come to exist** is governed by the global **registration mode** (§6.12): V1 runs in **closed mode** (admin-created accounts + invite links, exactly as today); invite/token, approval and open modes are designed and visible in admin settings, enabled post-v1.

**Email is mandatory on every account** — it is the identity for invites, password handling and the primary notification channel.

## 4. System Architecture

### 4.1 Three layers, strictly separated

```
┌────────────────────────────────────────────────────────────┐
│ DISPLAY LAYER — runs on the user's machine                 │
│   BetterTrack Web (React SPA, static files)                │
│   future: mobile app (Firebase push), CLI, widgets,        │
│   third-party API clients — all equal API clients          │
└──────────────▲─────────────────────────▲───────────────────┘
               │ REST /api/v1 (JSON)     │ WebSocket (push, post-v1)
┌──────────────┴─────────────────────────┴───────────────────┐
│ BUSINESS LAYER — BetterTrack Core (Node/Express service)   │
│   HTTP API · /docs · Services · Domain logic               │
│   Notifications · Jobs/Scheduler · Domain events           │
└──────▲──────────────▲──────────────▲───────────────────────┘
       │              │              │ AssetProvider interface
┌──────┴──────┐ ┌─────┴─────┐ ┌──────┴──────────────────────┐
│ DATA LAYER  │ │           │ │ External market data        │
│ PostgreSQL  │ │   Redis   │ │  yahoo (V1) · manual (V1)   │
│ (records)   │ │cache/queue│ │  crypto/gold providers later│
└─────────────┘ └───────────┘ └─────────────────────────────┘
```

**Principles (rules, not suggestions):**

1. **The display layer is dumb.** The SPA is static files served with long-lived cache headers; after load it runs entirely in the browser. Server cost per user ≈ API calls only.
2. **API-first.** Every feature is an API endpoint first; the web app is merely the first consumer. A future mobile app (or the owner's smart fridge) uses the same `/api/v1` — zero backend changes. The internal API is documented at **`/docs`** on the API origin (§6.13).
3. **All logic lives in the business layer.** The SPA never computes anything authoritative.
4. **Be polite upstream.** Every provider byte is cached; concurrent identical requests coalesce into **one** upstream fetch; N users viewing the same asset (or, later, the same live stream) cost one provider request. This is a correctness requirement, not an optimization (§5.3).
5. **Data sources are pluggable.** Nothing outside `providers/` knows Yahoo exists.
6. **Modular monolith.** One deployable backend with strict internal module boundaries. Realtime push (Socket.IO gateway, rooms per §4.5) is designed in but **implemented post-v1** — V1 clients stay fresh via TanStack Query refetch, which the architecture must keep sufficient.

### 4.5 Realtime gateway (designed now, built post-v1)

Socket.IO endpoint at `/ws` on the API origin, authenticated via the session cookie on handshake. Rooms: `user:{id}` (notifications, portfolio changes), `asset:{id}` (quote updates, Live Mode frames), `portfolio:{id}` (shared-portfolio viewers). Services publish typed **domain events** on the internal bus (`events/`, already implemented); the gateway and the notification dispatcher are subscribers. V1 explicitly ships without the socket: the SPA's refetch behavior must keep every V1 feature fully functional — the gateway is an enhancement layer for alerts, Live Mode and live shared views when they land.

### 4.6 Deployment topology

BetterTrack must be **flexible to set up anywhere**. Two supported modes, one global config (full env scheme in §11):

- **Subdomains mode** (default): three origins on one domain — `api.<domain>`, `web.<domain>`, `admin.<domain>`. Subdomain names are configurable; TLS terminates at the front proxy.
- **Ports mode**: no subdomains — everything on one host, each service on its own configurable port (e.g. `host:8080` web, `host:8081` admin, `host:3000` api).

| Service | Image / role | Notes |
|---|---|---|
| `web` | nginx serving `apps/web/dist` | Serves the SPA for **both** the web and admin origins (host- or port-based server blocks, §11); injects runtime config telling the SPA which app to mount |
| `api` | Node (apps/api, entry `server.ts`) | HTTP API + `/docs` (+ WebSocket post-v1) |
| `worker` | Same image, entry `worker.ts` | BullMQ processors |
| `db` | postgres:17 | Volume `pgdata`; nightly `pg_dump` to volume `backups` |
| `redis` | redis:7 | AOF persistence on |

The API is its own origin in both modes; the SPA calls it cross-origin with credentials. CORS allowlist and cookie attributes are **derived** from the topology config (§10, §11) — never hand-maintained. Health: `GET /api/v1/health`.

## 5. Data Layer

### 5.1 The provider abstraction (the "trackable" core)

Everything price-like flows through one interface:

```ts
type AssetRef = { providerId: string; providerRef: string }; // e.g. { 'yahoo', 'BAYN.DE' }

interface AssetProvider {
  readonly id: string; // 'yahoo' | 'manual' | future: 'coingecko', 'metals', ...

  search(query: string): Promise<AssetSearchResult[]>;   // catalog-fill only, never user-facing hot path (§6.2)
  getQuote(ref: AssetRef): Promise<Quote>;               // price, currency, prevClose, dayChangePct, asOf
  getHistory(ref: AssetRef, range: Range, interval: Interval): Promise<PricePoint[]>;
  getMeta(ref: AssetRef): Promise<AssetMeta>;            // name, symbol, exchange, currency, type
}
```

- A central **registry** maps `providerId → instance`. Services call `registry.for(asset)` — nobody else knows which provider is behind an asset.
- **`manual` provider** backs custom investments: `getQuote` returns the latest value point, `getHistory` the value points with carry-forward. Portfolio charts and P/L need zero special-casing for a house vs. a stock.
- **FX pairs are just assets** (`yahoo:EURUSD=X`), reusing the same caching/backfill machinery.
- Failure handling: timeouts (5 s), retry-once, circuit breaker; on failure the API serves the last cached value marked `stale: true` rather than erroring (stale-while-revalidate).
- Adding crypto/gold later = registering symbols or a new provider file. Nothing else changes.

### 5.2 Market data: Yahoo Finance via `yahoo-finance2`

Capabilities used: `search()` (catalog-fill), `quote()`, `chart()` (OHLC history, dividend/split-adjusted closes — backtests are total-return). Known risk: unofficial API, can change or rate-limit. Mitigations: (a) every byte cached and coalesced (§5.3), (b) outbound calls run through a queue with bounded concurrency + exponential backoff on 429/5xx, (c) user-facing search never blocks on Yahoo (§6.2), (d) the provider interface makes replacement a contained change, (e) UI disclaimers (§10).

### 5.3 Caching & upstream-politeness (a keystone, owner priority)

**The rule: one piece of upstream data is fetched once per TTL window, no matter how many users want it.** Never compromise freshness by more than the TTL; never multiply requests by users.

| Data | Where | TTL | Notes |
|---|---|---|---|
| Quote | Redis | 60 s | One fetch serves every user viewing that asset |
| History 1D (1 m candles) | Redis | 60 s | |
| History 1W (15 m) | Redis | 5 min | |
| History 1M (30 m) | Redis | 15 min | |
| History 6M/1Y (1 d) | Redis | 1 h | |
| History 5Y (1 wk) / Max (1 mo) | Redis | 6 h | |
| Provider search results (catalog-fill) | Redis | 24 h | Keyed by normalized query; also upserted into the asset catalog |
| Negative results (unknown symbol, 404) | Redis | 15 min | So repeated misses don't hammer the provider |
| **Daily closes** (backtests/portfolio history) | **Postgres `price_history`** | permanent | Nightly refresh + on-demand backfill (§9) |
| FX daily rates | Postgres (FX assets in `price_history`) | permanent | |

Mandatory mechanics (all already partially in `providers/`; P1 hardens them to this spec):

- **Request coalescing** on every cache key (`{providerId}:{providerRef}:{kind}:{range}`): concurrent misses trigger exactly **one** upstream fetch; all callers await the same promise (in-process) backed by a short Redis lock (cross-process).
- **Serve-stale-while-revalidate**: an expired entry is returned immediately (marked `stale`) while one background refresh runs.
- **Per-provider request budget**: bounded concurrency + minimum spacing; 429 from upstream opens the circuit breaker and stretches TTLs instead of erroring users.
- **Live Mode (post-v1) inherits this**: one polling loop per hot asset feeds a Redis ring buffer; N viewers = 1 upstream stream, auto-stops when nobody watches.

### 5.4 Currency handling

- Every asset keeps its **native currency**; all stored amounts are native.
- Conversion happens at read/computation time in one place: `services/currency` (current rates for quotes/totals, historical daily rates for backtests and portfolio history).
- Base currency is **EUR**, but always a parameter (`toBase(amount, currency, date?)`) — per-user base currency (Future Feature) is a settings field + passthrough, not a refactor.
- Display: money 2 dp, quantities up to 6 dp, weights 1 dp (stored at higher precision).

### 6.1 Authentication, accounts & sessions

- **Login** (`POST /auth/login`, email-or-username + password): argon2id (64 MiB · 3 · 1) for passwords and PINs; a dummy verify runs for unknown users so wrong-password and unknown-user are indistinguishable (`INVALID_CREDENTIALS`); a **disabled** account with the correct password gets `403 ACCOUNT_DISABLED` (§16 2026-06-16). User routes reject admin-kind sessions (`403 ADMIN_ACCOUNT_KIND`); admin routes answer 404 to everything else (§3, §6.12).
- **Second factor at login:** TOTP (`POST /auth/2fa/verify`) or an emailed code (`POST /auth/2fa/email-code`); a passkey sign-in counts as strong auth and skips 2FA. Enrolment under Control Center → Sign-in: TOTP (`/auth/2fa/enroll` → `/2fa/confirm`, `/2fa/disable`), email code (`/2fa/email/enroll|confirm|disable`, needs SMTP), 10 recovery codes issued with the first method (`POST /auth/2fa/recovery-codes`), `GET /auth/2fa/status`. Enabling or disabling 2FA revokes every other session.
- **Passkeys (WebAuthn):** multiple named passkeys per account — `POST /auth/passkeys/register/options|verify` (browser-only ceremony, password re-auth), `GET /auth/passkeys`, `PATCH|DELETE /auth/passkeys/:id` (management is bearer-callable under `account:security`, §16 2026-08-17), usernameless login via `POST /auth/passkeys/login/options|verify`.
- **Google sign-in** (env-gated `BT_GOOGLE_CLIENT_ID/SECRET`): `GET /auth/google/start` → `/callback`. An existing account whose e-mail matches a *verified* Google claim is linked and signed in; a new identity is parked in a one-time ticket (`GET /auth/google/register-ticket` → `POST /auth/google/register`) and completes on the register form under the active registration mode — Google never bypasses that mode. Linking/unlinking lives in Control Center → Connections (`POST /auth/google/link/start` + `GET /auth/google/link/callback` for the native app, §16 2026-08-18; `GET /auth/google/link-status`, `POST /auth/google/unlink`, refused when Google is the only sign-in method). Admin accounts cannot use Google or passkeys.
- **Sessions:** opaque 256-bit id in a signed httpOnly `bt_sid` cookie → Redis. *Stay signed in* (default) = a **fixed 30-day window** reset only by login or a correct PIN, never by ordinary activity. Unticked, or any OAuth-flow login on a PIN-less account = **ephemeral**: browser-session cookie, 45-minute sliding idle window, hard cap 6 h (§16 2026-07-11 §399). Password change, self-service reset, 2FA changes, admin disable/delete/role change and account deletion revoke all sessions. Session manager: `GET /auth/sessions`, `DELETE /auth/sessions/:id`, `POST /auth/sessions/revoke-others` (Control Center → Sessions).
- **Remembered devices** (#1327, §399 §B): `POST|DELETE /auth/remembered-device` binds the browser (`bt_rdid` cookie, 400 days) so the OAuth account chooser and re-login skip the *password* step only; the PIN is still required (`POST /auth/pin/quick-auth`) unless a ~15-minute post-PIN window is open; PIN-less accounts cannot be remembered; the minted session is always ephemeral. Management (`GET /auth/remembered-devices`, `DELETE /auth/remembered-devices/:handle`, `DELETE /auth/remembered-devices`) is session- or `account:security`-bearer-callable (§16 2026-08-18).
- **PIN app-lock** (V2-P2, V4-P0 (a)): `PUT|DELETE /auth/pin`, `GET /auth/pin/status`, `POST /auth/pin/verify`, `PUT /auth/pin/idle-timeout`. The client gates the UI on every app open and after `pinLockIdleMinutes` idle (default 10, max 1440); keystrokes anywhere land in the masked boxes and the DOM never contains a plain digit. 5 consecutive wrong PINs destroy the session and force a full login; a correct PIN renews the 30-day window. The PIN is a UI lock, not a session boundary.
- **Step-up re-auth:** `POST /auth/reauth` proves the current session's password (mints nothing; own throttle). Destructive account operations carry the credential **in the request body** — password, or TOTP/recovery code when enrolled — verified inside the same transaction (account deletion, data export, passkey delete, vault move-in/move-out, §16 2026-08-19).
- **Forced password change:** temp-password accounts get `403 PASSWORD_CHANGE_REQUIRED` on every route except login/logout/change-password/invite; the SPA traps into the change screen.
- **Registration modes** (all four live, V4-P4 (a); stored in `app_settings.registration_mode`, default `closed`): `closed` (admin-created + e-mail invites only), `invite_token` (admin-minted multi-use tokens with `maxUses`/expiry, `/admin/registration-tokens`), `approval` (applicants wait in `/admin/registration-requests`, approve/reject sends a decision mail in the applicant's language, `POST /auth/register` answers 202), `open`. `GET /auth/registration-info` tells the SPA which door is open; the register form carries the versioned legal-consent line (Terms · Privacy · Impressum · Cookies) and an OAuth continuation (`returnTo`) so app-native sign-ups return to the app (§16 2026-08-07). Invites: `POST /admin/invites` → 7-day single-use token → `GET /auth/invite/:token` + `POST /auth/accept-invite`; invites always create `user`-kind accounts.
- **Self-service password reset:** `POST /auth/password-reset/request` (generic acknowledgement, 250 ms response floor) → 1-hour single-use token → `POST /auth/password-reset/complete` (kills all sessions, then signs in or raises the 2FA challenge).
- **Password policy:** ≥ 8 characters (`MIN_PASSWORD_LENGTH`), no composition rules, top-common-passwords blocklist; temp passwords are 16-char CSPRNG strings shown once.
- **First run:** `POST /auth/first-run/complete` + the `/welcome` screen (`FirstRunGate`); accounts retired from the account-level paranoid mode see the one-time fresh-start notice (`POST /auth/fresh-start-notice/acknowledge`, §16 2026-08-29).
- **Account deletion** (V4-P2 (c)): `DELETE /account` — typed username, then in-body re-auth; hard-deletes portfolios, cash, tax, social edges, tokens, notifications, alerts, 2FA; chat rows are anonymised ("Deleted user") for the partner; all sessions revoked.
- **Data export** (V4-P6 (a)): `POST /account/export` (re-auth, 1 per 24 h) → async zip job → `GET /account/export` poll → `POST /account/export/download` one-shot token, 24-hour window; admin-only rows (operator notes, admin feedback columns) are excluded (§16 2026-08-29).
- **Progressive rate limiting** (§10): general 4500 / 15 min + burst 60 / 10 s, cooldowns 20 s → 60 s → 3 min → 10 min; login 25 / min / IP and 10 / 15 min / account with 30 s → 5 → 10 → 15 min; search 60 / min; bearer keys 120 / min unless an admin tier says otherwise.
- **Login UI:** "Continue with Google" on top (when configured), password form, OR divider, sign-up box at the bottom; the register page mirrors it (V5-P0 (a)).

### 6.2 Search & the local asset catalog (owner priority)

Search is **local-first**: `GET /search?q=` answers from the Postgres catalog (tsvector + `pg_trgm`, §5.5) in one round-trip, ranked exact symbol → symbol prefix → name → trigram similarity, 20 results, merged with the caller's own custom assets. Never a synchronous provider call.

- **Catalog fill:** every provider search upserts its results; the shipped seed list (`services/search/catalogSeedData.ts`: major global indices, the UCITS/US ETFs retail investors buy, DAX 40 / ATX 20 / S&P 500 constituents, top cryptos, major FX pairs, key commodities — each with its real provider ref); history backfill/metadata jobs (§9); users' custom assets (owner-scoped).
- **Provider fallback:** fewer than 3 market matches ⇒ a background, coalesced enrichment runs (`catalog.enrich`; a 60 s Redis guard per normalised query stops re-runs) and the response says `enriching: true`; the client refetches once and shows "Searching providers…". Misspellings work from the trigram index even when providers would 404.
- **Client:** debounce 300 ms, **min 1 character** (V2-P1 — a ticker like "V" works); the same hook drives the Assets → Search page, the buy dialog and the global **⌘/Ctrl-K palette**. Results carry symbol, name, exchange, type badge, currency and state-aware quick actions (buy/sell dialog, add-to-watchlist in place with a list picker, add-to-blueprint); clicking opens the asset page. Responses carry an ETag (§6.13).
- First touch of a market asset enqueues its history backfill (§9 `prices.backfill`).

### 6.5 Conglomerates ("Blueprints") & the Builder

**Model rules:** 0–50 constituents on write (a draft may be empty), ≥ 1 to activate; weights `0 < w ≤ 100` with ≤ 3 decimals; **status `active` requires Σ weights = 100 ± 0.01**, `draft` allows anything; names unique per owner; delete is a confirmed hard delete. A constituent is either an **asset** or, since V5-P6b, another of the owner's conglomerates (**nested**, `kind: 'conglomerate'`): cycles are rejected outright, nesting depth is capped at 3 (`MAX_NESTING_DEPTH`), and `GET /conglomerates/:id/resolved` returns the recursively flattened weights used by backtests, valuation and the calculator.

- **API:** `GET|POST /conglomerates`, `GET|PATCH|DELETE /conglomerates/:id`, `PUT /conglomerates/:id/positions` (bulk replace — the Builder's autosave), `POST /conglomerates/:id/activate`, `POST /conglomerates/:id/allocate` (§6.7).
- **The Builder** (`/workbench/blueprints/new`, `…/:id/edit`, full-screen): left — embedded search, click adds a position at weight 0; centre — per row symbol/name, weight input (0.001 precision) + slider, **lock**, remove; footer sum pill (green at 100.0 %, amber "87.5 % — 12.5 % left"); **Auto-balance** spreads `100 − Σ locked` equally over unlocked rows, **Normalize** scales unlocked rows proportionally to exactly 100 (error if locked alone ≥ 100); right — live preview (allocation donut + backtest 1Y/3Y/5Y/Max + headline stats) recomputed debounced after weight changes; every change autosaves the draft ("Draft — saved"); **Activate** validates and flips to `active` (the UI explains what active means, V2-P7).
- **AI draft** (§6.18): `POST /ai/conglomerate-draft` turns "30 % US tech, 30 % EU industrials, 40 % gold" into a draft resolved through the local catalog — always reviewed before save.
- **Sharing:** audience per blueprint via the shared picker (§6.9); a shared blueprint renders read-only at `/people/shared/conglomerates/:id` and public share links `/s/:token`; viewers can run **what-if sandboxes** (`POST /backtest/shared/:id/preview`) that never persist and never mutate the shared object.
- JSON export/import of conglomerates (including the legacy `conglomerate.py` format described in §14) is **not built** — planned, no issue filed.

### 6.6 Backtest engine

Pure function in `apps/api/src/domain/backtest.ts` — **API-only**. The shared `packages/domain` set (holdings, cash ledger, tax, series stats, settings scope — re-exported through one-line shims in `apps/api/src/domain/`) runs identically on the server, in the web vault engine and in the mobile conformance vectors; backtest and allocation (§6.7) are computed on the server only, which is why a vaulted portfolio (§6.16) has no client-side backtest:

```
Inputs:  positions[{assetId, weight}] (resolved through nesting), range 1Y·3Y·5Y·MAX,
         base currency, mode, rebalance, optional benchmark
Data:    daily adjusted closes from price_history; daily FX from FX assets
Method:  1. Window = requested range, clipped to the latest first-available date across
            positions ("common start") in `clip` mode — notice "Limited by TEM (data since …)".
            `cash` mode: a not-yet-listed constituent's share sits as uninvested cash until
            its first close; `redistribute` mode: its share is split equally over the listed
            constituents, then an entry-day rebalance to target weights (V3-P10 (a); entry
            markers on the chart; idle cash made visible in cash mode).
         2. Convert each series to the base currency with that day's FX rate; carry the
            last close forward over non-trading days per asset.
         3. index(t) = 100 · Σᵢ wᵢ · Pᵢ(t)/Pᵢ(t₀) — buy-and-hold of initial weights, unless
            rebalance ∈ {monthly, quarterly, yearly}: the portfolio returns to target weights
            on each schedule boundary (V4-P7; shares the entry-day primitive, reported as
            rebalanceEvents). Adjusted closes ⇒ dividends included.
Outputs: series[{date, value}], stats: total return %, CAGR, max drawdown, annualised
         volatility (σ daily × √252), best/worst day, per-position contribution;
         benchmark series + the same stats side by side with a delta column.
```

- **Benchmark** (one at a time): a preset (`^GSPC`, `^GDAXI`, `URTH`), any catalog asset, or another of the user's conglomerates run through the same engine with the same window/mode/rebalance (apples-to-apples). The benchmark always runs the full window — in cash mode the idle-cash drag is the honest comparison.
- **API:** `POST /backtest/preview` (positions from the Builder *or* a saved `conglomerateId`; `mode` defaults to `clip`, `rebalance` to `none`), `POST /backtest/compare` (N conglomerates → overlay + stats grid), `POST /backtest/shared/:conglomerateId/preview` (viewer sandbox). The V1 route `GET /conglomerates/:id/backtest` does not exist.
- Results are memoised in Redis for 1 h keyed by hash(positions + range + benchmark + mode + rebalance), scoped per user — slider-wiggling stays cheap; a paranoid transition purges the caller's memoised results before it commits (§6.16).

### 6.7 Invest Calculator (budget → buy list)

Pure function `allocateBudget` in `apps/api/src/domain/allocation.ts` (API-only, like backtest — §6.6). Inputs: the resolved active conglomerate, budget `B` in the base currency, mode `whole | fractional` (+ optional step, default 0.0001), and `atLeastOneShare`. Prices: current quotes converted per §5.4. **Hard guarantee: total cost ≤ B. Never overshoot.**

- **Fractional:** `qtyᵢ = (B·wᵢ)/pᵢ` rounded **down** to the step ⇒ spend ≈ B minus dust.
- **Whole shares:** `targetᵢ = B·wᵢ`; `qtyᵢ = floor(targetᵢ/pᵢ)`; `leftover = B − Σ qtyᵢ·pᵢ`; while any affordable share exists, buy one share of the asset that most reduces `Σ|actualᵢ − targetᵢ|` (tie-break: larger target weight, then input order); emit per-position qty, cost, actual % vs target %, Δpp, totals and leftover.
- **At least one share** (V2-P7, off by default): a position whose slice cannot afford one whole share gets exactly one, the remainder rebalances across the rest by weight — still under the same `Σ cost ≤ B` bound (a share dearer than the whole budget stays unbuyable).
- **Worked example** (mandatory test): B = 1000 €, BAYN.DE 30 % @ 25 €, NVDA 60 % @ 150 €, GOOGL 10 % @ 140 € ⇒ 12 × 25 + 4 × 150 = 900 €, 100 € left, GOOGL 0 % vs 10 % flagged "share price (140 €) exceeds its 100 € slice; raise the budget to ≥ ~1400 € or use fractional mode". Unreachable weights are always surfaced, never silently mis-weighted.
- Edge cases: any single price > B ⇒ unbuyable flag; market closed ⇒ last close with notice; stale quotes ⇒ warning banner.
- **UI** (`BudgetCalculator` on the blueprint detail page): amount stepper at selectable granularity 1 · 0.1 · 0.01 · 0.001 · 0.0001 · 0.00001 (V3-P0 (d)); `POST /conglomerates/:id/allocate`.
- **Buy flow:** result table → **Add to portfolio** → `TransactionDialog` pre-filled with one BUY per non-zero row (qty/price from the calculation, `executedAt = now`, editable, portfolio + cash-source picker, "pay from cash" with the cash-after preview) → confirm ⇒ bulk insert. ≤ 3 clicks from plan to recorded reality.

#### 6.8.2 Transactions & holdings

- **Transactions are the source of truth; holdings are derived** (`packages/domain/src/holdings.ts#reducePosition`, shared with the client vault engine and the mobile conformance vectors). `GET|POST /portfolios/:id/transactions`, `PATCH|DELETE /portfolios/:id/transactions/:txId`. There is **no dedicated ledger page yet**: `/portfolio/activity` renders a `ComingSoon` placeholder that points back to the Overview, where transactions are recorded and edited through `TransactionDialog` and the recent-transactions block (parked placeholder; §13.6 V6-3 names it).
- BUY/SELL carry quantity, price (native), fee, timestamp, note, cash source ("pay from cash" / "add proceeds to cash", §6.8.3) and a **source tag** — `manual`, `import:<broker>`, `sync:<provider>`, `standing-order` — rendered as a badge and filterable (V5-P0c).
- A SELL that would take the held quantity negative is **rejected** (`OversellError`); the only tolerance is the storage-quantum drift waiver of `1e-8` per stored row (§16 2026-08-05). An explicitly flagged **uncovered sell** (`allowUncovered` + `uncoveredEntryPrice`) is the deliberate exception for positions the user never recorded buying.
- **Average-cost basis** for holdings and the transaction rows' realised P/L: buys re-average `avg = (held·avg + qty·price + fee)/(held + qty)`; sells reduce quantity, average unchanged; realised P/L of a sell = `qty·(price − avg) − fee`. Tax reporting chooses its own cost-basis strategy per country (§6.8.4).
- **Idempotency** (V4-P2 (a)): mutations accept a client `Idempotency-Key` UUID (transactions create/update, every cash movement, value points, import apply); the stored response replays for 48 h.
- Transactions dated into any past year recompute that tax year live — there is no locking (§16 2026-08-19).

#### 6.8.3 Cash ledger, cash sources & cash flow

`packages/domain/src/cashLedger.ts` (exact-cents math; the withdraw-all bug of V3-P0 (e) is a pinned test).

- Every portfolio has a **Main** cash source plus named sources (`type: bank · retirement · cash · custom`): `GET|POST /portfolios/:id/cash/sources`, `PATCH …/sources/:sid`, `POST …/sources/:sid/archive|restore`, `POST …/sources/:sid/set-balance` (the app books the signed difference as a normal movement). - **TWR correctness:** cash-funded buys, sell proceeds and internal transfers are **never** external flows in the performance-% curve (`externalCashFlowsForTwr`); only deposits/withdrawals are.
- **Cash flow classification** (the V5-P9 "expense tracking" arc, re-homed under Portfolio → Cash rather than a separate top-level area): `/portfolio/cash` → Overview · Movements · Budgets · Labels · Accounts. Labels (tags) on movements (`/cash/tags`, `PUT /cash/movements/:id/tags`), auto-labelling **rules** with preview/apply (`/cash/rules`), per-label monthly **budgets** with a `budget.exceeded` notification once per period (`/cash/budgets`), `GET /cash/summary` and `/cash/trends`. - Standing orders (§6.14) book `cash-add` / `cash-deduct` movements on schedule.

#### 6.8.4 Dividends, realised P/L & tax

`packages/domain/src/tax.ts` (+ `services/tax`). Tax settings cascade **portfolio override → user default → system default**: user level `GET|PATCH /settings/taxes` (Control Center → Portfolio defaults), per portfolio `GET|PUT|DELETE /portfolios/:id/settings/tax`.

- **Dividends:** `GET|POST /portfolios/:id/dividends`, `DELETE …/dividends/:id` — holding, date, gross amount, landing in a chosen cash source, tax-mode aware.
- **Modes:** `none` (default; V2 behaviour byte-identical), `manual_per_trade` (every sell/dividend takes an optional tax amount-or-% with a configurable **default** prefilled and editable per trade), `country_specific`, `custom`.
- **Countries** (`SUPPORTED_TAX_COUNTRIES`): **AT** — 27.5 % KESt on realised gains and dividends, moving-average cost basis, losses offset gains **within the calendar year** with a refund of tax already paid that year, hard reset on Jan 1, no cross-year carry (§16 2026-07-06); **DE** — 25 % Abgeltungsteuer + 5.5 % Soli on the tax, **FIFO**, €1,000 Sparer-Pauschbetrag (unused remainder does not carry), separate loss pots (Aktien vs Sonstige) that do carry; **FI** — 30 % capital-income tax, 34 % above €30,000, gains/dividends/losses in one within-year pool, no carry (#635 — a third country the plan never listed).
- **Custom rule engine** (`CustomTaxParams`): `ratePct`, `lossOffset`, `refund`, `yearReset`, `carryForward`, `costBasis ∈ {moving-average, fifo}`; AT is expressible as a parameter set (`AT_AS_CUSTOM_PARAMS`, pinned by test).
- Withholdings and refunds post as distinct cash movements against the trade's source. Mode/country switches apply forward from the switch. **Tax years are living documentation:** every year is always mutable, reports recompute live, `GET /settings/taxes/years` lists last-changed markers; no lock, no unlock ritual (§16 2026-08-19).
- **Reports:** `/portfolio/tax` → `GET /portfolios/:id/reports/tax-years`, `…/tax-years/:year` (realised P/L + dividends + tax per year with per-position drill-down), `…/:year/export.csv`, and the print layout `/portfolio/tax/print` for PDF.

#### 6.8.5 Custom assets

API: `GET|POST /custom-assets`, `PATCH|DELETE /custom-assets/:id`, `GET|PUT /custom-assets/:id/value-points`, `GET /custom-assets/recategorization` + `POST …/dismiss` (the one-time re-categorise banner). Custom assets are created and their value points edited from the Portfolio Overview's dialogs (`CustomInvestmentDialog`, `ValuePointEditor`); the routed list page `/assets/custom-assets` (and the legacy `/portfolio/custom-assets`) is a `ComingSoon` placeholder — parked.

- Category is a real taxonomy — `stock · etf · crypto · commodity · cash_like · other` (V3-P2 (a)): a custom "stock" counts as Stocks in donuts, category views and analytics; there is no CUSTOM slice anywhere.
- **Value points** (date, value), one per day, carry forward between points; the per-asset **smoothing** toggle (default off) interpolates linearly between marks in every series reconstruction while mark-day values stay exact.
- A custom asset behaves like any asset: chartable, holdable (optional initial BUY at creation), watchable, usable in blueprints and backtests.

#### 6.8.6 Overview, value series, snapshots & analytics

- **Overview** (`/portfolio`): Net Worth header (market value, invested, unrealised P/L €/%, day change, cash split / liquidity), performance chart with ranges **1D · 1W · 1M · 3M · 6M · 1Y · 5Y · MAX** (1D/1W render a real intraday curve, V5-P1 (d)), holdings list, top winners/losers (day % / total P/L), allocation donuts (asset / type), recent transactions, quick add. The overlay/compare machinery lives in Analysis, not here (owner: "too technical").
- **Series:** `GET /portfolios/:id/history?range=` reads the precomputed **daily snapshot table** (value, cost, P/L, per-source cash; V5-P1 (a)) with the live "today" point computed fresh; backdated edits invalidate exactly the affected range (invalidation rules in `services/portfolio/portfolioSnapshots.ts`); custom assets contribute carried-forward or smoothed points. `GET /portfolios`, `GET /portfolios/:id` and the history read answer conditional requests with a body-derived **ETag** (`If-None-Match` → 304; no `Last-Modified` validator is emitted; V5-P1 (b)).
- **Analysis** (`/portfolio/analysis`, V3-P9): `GET /analytics/portfolios/:id/series` — per-asset hide/show, include/exclude by category, free date range, value vs performance-% modes, smoothing-aware; per-asset contribution table; **compare** against any catalog asset/index, another of the user's portfolios or a blueprint (`ANALYTICS_COMPARE_KINDS`) with side-by-side stats; **inflation** mode against `hicp-at`, `hicp-eu`, `cpi-us` or a flat %/yr (each preset shows its effective %/yr, V4-P0 (c)).

#### 6.8.7 Broker imports

`/portfolio/import` (feature flag `imports`; `docs/imports.md` is the binding pipeline description). `GET /imports/brokers` → `POST /imports` (upload → broker autodetect or manual pick → normalised staging batch: buys/sells/dividends/cash, fees where derivable) → `GET /imports/:batchId` (preview with mapped/unmapped/duplicate/error flags) → `PATCH /imports/:batchId/rows/:rowId` (pin an unresolved instrument, incl. "create a custom asset on the spot") → `POST /imports/:batchId/apply` (transactional, idempotent, into a chosen portfolio + cash source) or `DELETE`.

- Mappers: **Trade Republic, George (Erste), Flatex, IBKR** (source tags `import:<broker>`); dedupe against existing rows by content hash (date + instrument + qty + price); per-row errors are reported while the rest lands.
- **Generic staging path** (§16 2026-08-29): a file no mapper claims is sniffed, its columns labelled and rows classified individually; an AI column proposal (§6.18) is surfaced **read-only** — confirming it has no write path (**planned, owner decision #964**), and a cash row without a booking-type column is reported, not booked.
- Imported dividends respect cash source and tax mode. A portfolio with import batches refuses vault move-in (§16 2026-08-28).

### 6.13 API access, OAuth, webhooks & `/docs`

- **Docs:** `GET /openapi.json` (OpenAPI 3 generated from the zod contracts in `packages/contracts`) and `GET /docs` (Scalar UI) are served **publicly** at the API origin root; CI fails when a mounted route is missing from the document (`check:openapi-coverage`). - **Personal API keys** (`btk_…`; `GET|POST|DELETE /settings/api-keys`; Control Center → API): scoped, hashed at rest, revocation-only. **Scopes** (`API_KEY_SCOPES`, 21 values): `portfolio:read`, `portfolio:write`, `workboard:read`, `workboard:write`, `market:read`, `social:read`, `social:write`, `notifications:read`, `notifications:write`, `chat:read`, `chat:write`, `account:security`, `alerts:read`, `alerts:write`, `cash:read`, `cash:write`, `mirrorchain:read`, `mirrorchain:write` (participation-only allowlist, never administration, §16 2026-08-04), `vault:sync` (opaque encrypted-blob sync only, §16 2026-08-04), `feedback:write`, `feedback:read`. App-native registration returns into the authorize flow (§16 2026-08-07).
- **Bearer parity** (V4-P1): `loadBearerAuth` resolves keys and tokens; `MODULE_POLICIES` classify every route group by method; narrow allowlists open exactly the vault-sync, account-security, mirrorchain-participation, passkey-management, tax-documentation and first-party-grant routes. **Session-only by design:** vault transitions and media changes, webhooks, OAuth-app management, admin, `/ai`, `/expenses`. Bearer requests skip CSRF; cookie mutations need `X-Requested-With: BetterTrack` + an allowed `Origin`.
- **Outbound webhooks** (V5-P10; `GET|POST /settings/webhooks`, `PATCH|DELETE …/:id`, `GET …/:id/deliveries`): per-event-type subscriptions (≤ 20 per user), payload signed `sha256=` HMAC-SHA256 over `${timestamp}.${body}`, 5 attempts with exponential backoff, SSRF re-check on every attempt, **auto-disable after 5 consecutive failures** (audited; manual re-enable), 30-day delivery log.
- **Key governance:** admin-configurable **rate-limit tiers** (`/admin/api-key-tiers`, `PATCH /admin/api-keys/:id/tier`; base 120 / min), per-key **audit trail** (`lastUsedAt`, bounded request log of method/path/status incl. denials, `GET /admin/api-keys/:id/audit`).
- **Developer platform page** (`/developer`): the user-facing entry; `/developer/mcp`, `/developer/logs`, `/developer/oauth-apps` are parked placeholders.

### 6.16 Privacy modes — discreet mode & paranoid vaults

- **Discreet mode:** per-user toggle (account menu; `PATCH /settings/account { discreetMode }`) that hides every absolute money amount on every surface — balances, values, cash, transaction amounts, tooltips, chart axes — and shows percentages/relative values; a sweep test asserts zero absolute amounts with the toggle on.
- **Paranoid vaults** (V5-P13 arc b, owner redefinition 2026-08-19; `docs/paranoid-design.md` is the binding text and the §16 rows of 2026-08-19/20/21/22/28/29/30 amend it): an account owns N **vaults**; a vault is a storage config — BetterTrack server, a **separately authenticated Google Drive connection**, or both — opened only by its **12-word BIP39 seed phrase** (the sole credential; lost phrase = lost vault, no escrow). **Portfolios move into a vault** (`POST /portfolios/:id/vault/move-in` with the capture↔commit revision token from `GET …/vault/revision` and in-body step-up), which hard-deletes the portfolio's server cleartext and re-homes it into the vault's encrypted doc set; **move-out** (`POST …/vault/move-out/challenge` → `…/move-out`, phrase-bound to `GET …/vault/lifecycle`) restores it under the same UUID. Server surface: `/vaults` (CRUD, per-doc CAS + history, media transitions with attested server candidates, signed retired-data purge), `/drive-connections` (token-free registry, `drive.file` scope, visible "BetterTrack Vaults" folder, ownership-checked digest-named namespace). **Feature kill is per vaulted portfolio only** (`vaultedPortfolioGuard` registry): sharing, server stats, jobs, imports and portfolio-scoped bearer access die for that portfolio while every other portfolio keeps full functionality; valuation, stats and tax for vaulted portfolios run client-side through `packages/domain`; cross-portfolio aggregates carry a "+ N locked portfolios" qualifier; `VaultSyncChip` shows sync state. Device custody: the stored phrase is wrapped by a per-device password that is never cached across sessions (or stored plain behind a strong warning); a step-up-gated, auto-expiring **QR handoff** moves a phrase to the phone. Legacy account-level paranoid mode (`/account/paranoid/*`, `/vault`, `users.privacy_mode`, `MeResponse.privacyMode` — deprecated) survives **only for accounts already in it**: the client-side "Set up" entry was removed on 2026-08-30, so no normal account can enter it, and the server surface goes when the owner-run §17 backup + wipe retires the last such account (E9 shipped; §16 2026-08-29, 2026-08-30). Epics E0–E10 are closed; the Drive-only e2e arc is env-gated by `PER_VAULT_DRIVE_PROVISIONING_AVAILABLE`.

### 6.17 Mirrorchain — group portfolios

`docs/mirrorchain-design.md` is binding. One logical portfolio replicated as a synced copy in every member's account: `GET|POST /mirrorchain/chains`, `POST /mirrorchain/chains/convert`, invites through friends (`POST /mirrorchain/chains/:id/invites`, `GET /mirrorchain/invites`, accept/decline/revoke), `GET …/:id/members`, `…/activity`, `PATCH …/:id` (rename), `POST …/:id/transfer` (ownership), `PATCH …/members/:userId/role` (`owner · manager · member`, ≤ 16 members), `DELETE …/members/:userId` (kick), `POST …/:id/leave`, `DELETE …/:id` (dissolve). No cloud AI, no API-token providers, no per-call billing anywhere in the product (§16 2026-07-22). ## 7. Display Layer — Web App

### 7.1 Principles

- Pure static SPA (Vite build → `dist/`), served by nginx with immutable cache headers, `index.html` no-cache. **One build, two apps:** nginx injects `window.__BT__ = { app: 'user' | 'admin', apiOrigin, … }` per origin; `App.tsx` mounts `UserApp` or the lazily loaded `AdminApp` from that flag alone — there is no path-based `/admin` on the user origin. The SPA talks to the API origin cross-origin with credentials (§4.6, §10).
- **Server state:** one TanStack `QueryClient` (`staleTime` 30 s, `refetchOnWindowFocus` off, `retry` 1; per-query overrides where a server TTL says otherwise), request dedup, conditional requests where the API offers them. **Realtime:** a Socket.IO client at `/ws` with credentials, reference-counted `asset:{id}` / `portfolio:{id}` rooms, Live-Mode watch/unwatch and presence heartbeats; a socket error is silent and polling takes over (flag `realtime`).
- **Design language:** the **Origin** system (`ui/origin`, `styles/origin.css`) — dark-first with **system / dark / light** themes per device (`bt.ui.theme`, boot-stamped before the bundle loads, toggled in Control Center → Appearance), semantic data-viz colour (green gains / red losses, gold accent), `de-AT` number formatting (1.234,56 €) under the active locale.
- **i18n:** EN is the source of truth and default, DE the full translation; adding a language = one message file + one registry entry (`docs/i18n.md`); a hardcoded UI string fails CI; the server-stored locale syncs at login, the admin console keeps its own.
- **PWA:** manifest + one root-scoped service worker that precaches hashed assets, **never intercepts `/api`**, and serves a branded offline page on failed navigations (§16 2026-08-04); persistent storage requested; web-push subscription reuses the same registration. Install affordance (V5-P13b, #1713): one compact card, out of the document flow, that captures `beforeinstallprompt` where it fires and shows an Add-to-Home-Screen coach mark on iOS where it never does; absent once the app runs installed, dismissible, and the dismissal is permanent. Standalone windows are detected (`display-mode: standalone` + `navigator.standalone`) and get the shell's own back button, cross-origin links sent out to the real browser, and status-bar compensation. A dedicated 180×180 opaque `apple-touch-icon` is the iOS idiom; the manifest carries `lang`/`dir`/`orientation`/`categories`/`display_override` but **no `shortcuts`** (one manifest carries one language, so every label would ship untranslated). Desktop-first, fully usable at phone widths (V5-P13b; 390×844 / 360×800 on every gate checklist).
- **Gates:** `RequireUser` → `FirstRunGate` (`/welcome`) → the app; the **PIN gate** wraps everything on app open and after idle (§6.1); `403 PASSWORD_CHANGE_REQUIRED` traps into the forced-change screen; 401 clears the session; 429 raises the rate-limit toast; every mutation sends `X-Requested-With: BetterTrack`.
- **Placeholders:** `ParkedPage` ("In the works", with pointers to the live surface) and the older `ComingSoon` component still ship for the parked surfaces named in §6 and §7.2 — the plan's V1 promise "not-yet-built surfaces say Coming soon instead of not existing" still holds for them; §13.6 V6-3 rules each one at v6 prep. Skeleton loaders, error boundaries with retry and designed empty states everywhere else.
- **Anti-bloat (owner, binding):** the main things stay immediately visible; niche sub-features fold away compact — no shipped feature may make the app feel more bloated.

## 10. Security & Privacy

- **Closed by default:** every route requires a session except login/invite/health/docs; admin routes require the admin account kind; user routes reject admin sessions (§3). Object access is always ownership-scoped in repositories (`WHERE owner_id = session.user` — no IDOR by construction); social reads additionally require live friendship + visibility (§6.9).
- **Passwords & PIN:** argon2id (memory 64 MB, iterations 3, parallelism 1) for both; session rotation on login; all-session invalidation on password change/disable. Sessions: 30 days, renewed by login or PIN verify (§6.1). API keys (post-v1): hashed at rest, never expire, revocation-only, never logged.
- **Cookies/CSRF/CORS:** httpOnly + `SameSite=Lax` + `Secure`; state-changing requests require `X-Requested-With: BetterTrack`. The API's CORS allowlist is exactly the derived `WEB_ORIGIN` + `ADMIN_ORIGIN` (§11) with credentials; all origins share one registrable domain (or one host in ports mode), keeping `Lax` cookies flowing. Strict `Origin` check on state-changing requests (and the future socket handshake).
- **Headers:** helmet with strict CSP (self + the API origin for connect-src; no third-party assets — fonts/icons bundled).
- **Validation:** every request body/query parsed by the shared zod schema; unknown fields rejected.
- **Progressive rate limiting** (Redis, replaces the old fixed-window blocks — owner directive #79):
  - **Principle:** normal use is never limited; bursts get short pauses; only sustained abuse gets long cooldowns. Limits reset quickly after good behavior (escalation level decays after ~15 min without violations).
  - **General API:** generous steady-state allowance (**9000/15 min/user**, i.e. 600 req/min), fronted by a **600 req/30 s** burst window on the same key and ladder; on exceeding either: cooldown **10–30 s**, then per repeated violation **1 min → 3 min → 10 min** (cap). 429 responses carry `retryAfter` in the body **and** a `Retry-After` header (CORS-exposed, since the SPA is cross-origin); the SPA shows the existing toast and does not retry the rate-limited request.
  - **Sizing rule (owner directive 2026-09-02):** every limiter normal use can reach must clear the **modelled normal-use bar** — one active user with two tabs — by at least **3×**. The bar, the arithmetic and the whole limiter table live in one place in `apps/api/src/config/env.ts` and are pinned by `config/__tests__/rateLimitTable.test.ts`. Authenticated traffic is keyed **per user**; the IP fallback is for anonymous callers only, so two accounts behind one address never share a bucket.
  - **The strict set is exempt from that rule and is not loosened:** login (per-IP and per-account, which also backs every re-auth ladder), **PIN set and PIN verify** (both argon2id at 64 MiB), registration, password reset, friend-request creation, and feedback capture. If normal use trips one of those, the client's behaviour is what gets fixed.
  - **Login (stricter, security-sensitive):** ~**10 failed attempts → 30 s cooldown**, next batch → **a few minutes**, escalating to **10 min+** for persistent hammering; per-IP and per-account tracked separately. PIN verify uses the login schedule.
  - Search keeps its own modest per-user budget; admin endpoints get the general schedule.
- **Share/invite tokens:** ≥ 128-bit CSPRNG, url-safe, constant-time compare, revocable, never logged.
- **Outbound safety:** provider HTTP fixed to known hosts (no user-supplied URLs ⇒ no SSRF surface); secrets only via env; `pnpm audit` in CI.
- **Privacy:** PII = email only; user deletion cascades all data incl. friendships; email log stores metadata, never bodies; no analytics/trackers; logs (pino, JSON) exclude bodies and tokens. Backups: nightly `pg_dump`, 14-day rotation, restore procedure in README.
- **Disclaimers (footer + asset pages):** market data comes from an unofficial source and may be delayed or inaccurate; BetterTrack is not investment advice.

## 11. Configuration & Environments

**Principle: the app must be flexible to set up anywhere.** One global config drives the whole topology; every name and port is overridable; nothing origin-shaped is hardcoded.

| `ADMIN_EMAIL` / `ADMIN_PASSWORD` | — | seeds the first admin on first boot only |

**Origin derivation** (in `config/env.ts`, single source of truth consumed by CORS, cookies, link generation, the SPA runtime config and nginx templating):
- `subdomains` mode: `https://{BT_SUB_X}.{BT_DOMAIN}` for each service (TLS assumed at the front proxy).
- `ports` mode: `http(s)://{BT_DOMAIN}:{BT_PORT_X}` — one hostname (may be an IP or `localhost`), no subdomains, everything separated by port.

**nginx layout** (`infra/nginx/`): templated at container start from the same env.
- *Subdomains mode:* one nginx with three `server` blocks by `server_name` — `web.*` serves the SPA (user runtime config), `admin.*` serves the same SPA (admin runtime config), `api.*` proxies to `api:3000`.
- *Ports mode:* the same three server blocks keyed by `listen` port instead of hostname.
- In both modes the SPA server blocks inject `window.__BT__` (app kind + API origin) via a generated `config.js` — one web image serves every topology.

**Dev:** `docker compose -f infra/docker-compose.dev.yml up` (db+redis) → `pnpm dev` (vite + tsx watch + worker); defaults to ports mode on `localhost`. Migrations `pnpm db:migrate`; seed creates the first admin + a demo user. **Prod:** `docker compose up -d` in `infra/` — five services (§4.6); deploy = build, migrate, restart.
